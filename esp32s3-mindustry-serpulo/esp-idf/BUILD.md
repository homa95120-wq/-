# Сборка и прошивка прототипа ESP-IDF

Требуется: ESP-IDF v5.3.x + инструментарий xtensa/esp32s3.

```bash
cd esp32s3-mindustry-serpulo/esp-idf

# Выбрать цель
idf.py set-target esp32s3

# Собрать
idf.py build

# Собрать объединённый образ для прошивки одной командой (адрес 0x0)
cd build
esptool.py --chip esp32s3 merge_bin -o mindustry-esp32s3.bin @flash_args

# Прошить (после подключения платы)
esptool.py --chip esp32s3 -p /dev/ttyUSB0 -b 460800 write_flash 0x0 mindustry-esp32s3.bin

# Монитор порта
idf.py -p /dev/ttyUSB0 monitor
```

Готовая сборка публикуется автоматически в релиз
`esp32-mindustry-fw-latest`:

**⬇ https://github.com/homa95120-wq/-/releases/download/esp32-mindustry-fw-latest/mindustry-esp32s3.bin**

Workflow: `.github/workflows/esp32-mindustry-firmware.yml` (собирает на каждый
push в `main`, обновляет ассеты релиза).

## Что делает прототип (этап 4)

- Инициализирует активный сектор 128×128 тайлов (структура ~1.4 МБ — **в PSRAM**)
- Прокладывает водяные трубы от источника к резервуару
- Ставит генератор, батарею и потребитель (турель) — считает баланс энергии за тик
- Прокладывает конвейеры и подаёт на них предмет (медь)
- Спавнит вражеского юнита и снаряд — моделирует полёт и попадание
- Пробует построить путь A* от (25,25) к (20,2)
- Каждую секунду выводит статистику в ESP_LOG (tick, волна, баланс энергии, дефицит, юниты, снаряды)

## Проверено

1. **Компиляция** — код собирается ESP-IDF 5.3.1 в GitHub Actions (workflow выше),
   на выходе `mindustry-esp32s3.bin`. До 2026-10-24 в проекте были ошибки сборки:
   `REQUIRED` вместо `REQUIRES` в CMake, передача `sim_sector_t*` вместо
   `combat_world_t*`, статический сектор 1.4 МБ (не влезает в 512 КБ SRAM) —
   исправлено: сектор выделяется в PSRAM через `heap_caps_malloc`.
2. **Логика** — подсистемы дополнительно прогнаны на хосте (`g++`, 300 тиков):
   предмет едет по конвейеру, вода доходит до резервуара, энергобаланс 100/40,
   путь A* находится.
3. **На реальной плате не измерялось** — этап 5 дорожной карты всё ещё требует
   замеров FPS/лимитов объектов на железе.

## Известные ограничения прототипа

1. Требуется плата с **8 МБ PSRAM** (N16R8) и 16 МБ flash.
2. `fluid_tick` использует статический массив `delta` 128×128 float (~64 КБ в BSS) —
   помещается в SRAM, при необходимости переносится в PSRAM.
3. `pf_nodes` в pathfinding (~40 КБ в BSS) — аналогично.
4. Нет сетевого протокола клиент-сервер (Wi-Fi TCP) в прошивке — только локальный
   демо-цикл. Протокол описан в `docs/PROTOCOL.md`, TCP-вариант есть в
   `micropython/main.py`.
5. Нет дисплея/рендеринга — headless-сервер, как и требуется для клиент-серверной
   архитектуры.
